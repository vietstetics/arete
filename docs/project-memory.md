# Arete project memory

Arete is a personal fitness app built around training plans, workout logging, camera-based rep tracking, nutrition, and recovery. The workspace is named `jarvis`, and earlier JARVIS names remain in package metadata, native identifiers, and storage keys. The configured GitHub upstream is `vietstetics/arete` on `main`.

## Architecture and development

- The root HTML files are the web entry points. Many pages contain inline CSS and classic JavaScript, and use ES modules under `features/` for focused data, services, repositories, and UI. Some modules bridge to inline code through globals and custom events. Start at the actual page entry point and trace both kinds of scripts.
- `package.json` defines the test suites and development scripts. `npm.cmd run dev` works from Windows PowerShell and serves the app over the local network. `scripts/dev-server.mjs` and `js/devtools.js` support a paired phone-to-computer video workflow. `test-videos/` contains local test media. The pose extraction, tracker evaluation, video recognition, browser smoke, and velocity accuracy scripts live in `scripts/`.
- The web app uses the root static files on Vercel, with serverless routes in `api/`. `vercel.json` sets revalidation headers and redirects the former Sleep page. The PWA uses `manifest.webmanifest` and `sw.js`, which serves HTML network-first and uses stale-while-revalidate for assets.
- Home startup runs three checks in `js/splash.js`: saved data and storage, live Home components, and app screen documents with their directly linked scripts and styles. The launch overlay has a deadline and an inline fallback. The retry notice surfaces incomplete startup, and `window.__areteStartup` records the checks for debugging. Run `node scripts/test-startup-browser.mjs` to check startup, retries, offline cache behavior, missing assets, and timeouts.
- Capacitor config uses app ID `com.jarvis.fitness` and web directory `www/`. `npm.cmd run build:web` regenerates the copied web bundle, and `npm.cmd run sync` also runs Capacitor sync. The generated `www/`, `android/`, and `ios/` directories are gitignored. Native plugin source and setup live in `native/` and `scripts/wire-native.mjs`. iOS builds require Xcode.
- Source and data generation include `scripts/build-machine-db.mjs`, `scripts/build-muscle-db.mjs`, and the plate-detector scripts in `scripts/plate-detector/`. The optional ONNX model path is documented in `models/README.md`. Use `backups/` and old local worktrees as historical references if needed.

## Data and integrations

- The app uses local-first browser storage. Check the existing key and payload before changing a producer or consumer. Examples include `jarvis_active_workout`, `jarvis_templates`, `jarvis_prs`, `jarvis_steps`, and `jarvis_health_*`. The compact camera record has its own `arete_velocity_sets` store and can also be carried on logged workout sets.
- `js/authguard.js` requires a session. With Supabase configured, `js/auth.js` supports cloud login and debounced mirroring of `jarvis_*` keys to the authenticated user's `user_data` row. Otherwise the app uses a device account and an `arete_session` flag. Standalone `arete_*` keys are outside that generic cloud snapshot. Older integration notes describe earlier behavior, so check the current guard and snapshot before changing auth or sync.
- `features/health/` separates provider adapters, storage, sync, deduplication, preferred source selection, and UI. Apple HealthKit and Android Health Connect use the read-only `HealthPlugin`. Sync maintains incremental cursors and deduplicates provider records and overlapping Arete workouts. Source preferences avoid summing multiple providers for a metric, manual steps are protected, and imported sleep can be queued for explicit acceptance even though the standalone Sleep page was removed.
- The dedicated Steps flow has its own `StepCounter` plugin, repository, sync, date and streak logic. iOS uses `CMPedometer`. Android supports Health Connect and a native step-counter sensor fallback. Native source is in `native/ios/` and `native/android/`.
- `js/wearables.js` manages the older wearable connections and cached statistics. `api/whoop/token.js`, `api/strava/token.js`, and `api/oura.js` provide integration routes. Provider availability depends on configuration and permissions. `api/analyze-food.js` handles photo nutrition estimates, and `api/parse-workout.js` handles AI workout parsing. Integration setup is in `api/integrations/README.md`.

## Nutrition

- The diary stores date-keyed entries in `jarvis_nutrition_log`, goals in `jarvis_nutrition_goals`, and water separately. `jarvis_nutrition_today` is the lightweight Home handoff. A logged entry carries base macros, a portion multiplier, and optional detailed nutrients in `ext`. Coverage depends on the food source and available fields.
- Barcode scanning uses the native ML Kit plugin in Capacitor or browser camera paths on the web. Open Food Facts adds product data. The food database, barcode normalization, manual entry, and estimated meals are implemented in `nutrition.html`.
- The hexagon chart in **Nutrition → Nutrients** is on GitHub in commit `93dfcda`. Macros plots protein, carbs, fat, and calories against personal goals, plus fibre and omega-3 against the existing daily values. Micros plots vitamin C, vitamin D, B12, iron, calcium, and potassium against existing daily values. The outer ring represents 100%, labels retain over-target percentages, and missing values use a dash. Theme tokens set the ink and green accents.
- The local Cronometer-inspired changes add optional food times, daily notes and completion, weekday goal overrides, custom nutrient targets and limits, detailed custom foods, diary-derived reusable recipes, a fasting timer and history, and search by nutrient using the existing catalogue. Reports show date-range daily averages and a selected nutrient trend, with a completed-day filter, CSV download, and print view. The report excludes missing nutrient data from that nutrient's average.
- The remaining consumer feature scope includes recurring diary items, scheduled fasts, recipe URL import and sharing, biometric definitions and logging, nutrition scores, paired nutrient/biometric charts, voice logging, and nutrition coaching. Catalogue breadth, nutrient coverage, and device integrations depend on available data and providers. The public product comparison is the reference for checking coverage. [Cronometer Basic and Gold comparison](https://cronometer.com/gold/)

## Training camera and coaching

- `features/standard/` handles body pose, per-lift motion features, smoothing, and rep start/finish classification. `features/velocity/` handles the measured-point source, frame timing, scaling, live and offline pipelines, geometric plate tracking, compact records, workout handoff, coach metrics, and prediction models. `curl-lab.html` is the camera/controller entry point used from the workout logger.
- Preserve the agreed measurement source. Machines and cables use the moving grip or contact point, with the ankle landmark for leg curl/extension. Free weights use the weight. Rep counting can still use pose independently. Relative pose tracking carries its own label when usable weight tracking or real-world scale is unavailable.
- In the live rep-standard flow, rep 1 establishes the reference distance for the set. Mean concentric speed uses that distance divided by concentric time. Timing follows captured frame timestamps and interpolates line crossings. Short or unclear reps retain their status and have no live velocity. Long gaps in the tracked point can invalidate the velocity. The offline plate validation lab also reports each reconstructed lift's own distance and speed for reference-device comparisons.
- Workout readiness in `features/velocity/services/readiness.js` compares today's first tracked set with the same exercise and load from earlier sessions, matching equipment where known. It requires clean m/s values and at least two comparable sessions. The coaching prototype keeps captured metrics, estimates, and entered effort distinct.
- The lab and automated tests cover synthetic motion and software behavior. Claims about agreement with a transducer require real paired measurements and device testing. See [tracking plan](velocity-tracking-plan.md), [implementation status](velocity-implementation-status.md), [accuracy protocol](velocity-accuracy.md), [prediction methods](velocity-prediction-methods.md), and [coach prototype testing](coach-prototype-testing.md). [Coach plan](coach-plan.md) describes a wider product roadmap, including a real multi-account backend and coach/client review workflow.

## UI conventions

- Follow the actual page and shared theme. `css/theme.css` overrides older page tokens with the light Apple-style palette, near-white grouped canvas, white rounded cards, dark ink, and green accents. `css/touch.css`, `js/mobilenav.js`, and page media queries govern mobile interaction and navigation. `css/motion.css`, `js/motion.js`, `js/feel.js`, and `js/splash.js` handle motion, touch feedback, and launch.
- Preserve the app's existing responsive layout, typography, readable values, reduced-motion behavior, and clear empty/unavailable states. [Redesign PRD](redesign-prd.md) records design direction and includes historical screens and placeholders.

## Local work at the 23 November 2026 snapshot

- `main` matched its known upstream at `93dfcda` before the memory files were added. The working tree already contained independent edits in `index.html`, `nutrition.html`, and `workouts.html`, plus the files below. Recheck Git status for current state.
- `features/nutrition/services/weightTrend.js` and its tests support a bodyweight log and smoothed trend wired into the local Nutrition and Home changes. The Nutrition view accepts kg or lb and stores dated measurements in kg. The trend blends 10% of each daily weigh-in, with an elapsed-day adjustment for gaps. Weekly rate requires at least four weigh-ins across at least seven days.
- `features/training/services/progression.js`, its tests, and the local workout edits implement double progression using prior working sets, rep ranges, target RIR, an equipment-specific load step, and a readiness override. These local additions have a separate release status from the pushed chart.
